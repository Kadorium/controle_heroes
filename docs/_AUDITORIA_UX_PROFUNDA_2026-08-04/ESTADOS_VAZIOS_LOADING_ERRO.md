# Estados vazios, loading e erro

Data: 2026-08-04.

## 7.1 Empty state de tabela

| Local | Componente usado | Qualidade |
|---|---|---|
| OrdersListPage | `EmptyState` + `orientation` ("Ajuste o status ou crie um novo pedido.") | Boa — mensagem + orientação, mas sem botão de ação direta |
| InvoicesListPage | `EmptyState` + `orientation` | Boa, mesmo padrão |
| **PayablesListPage (fallback)** | `EmptyState` message-only, **renderizado junto com a tabela vazia, não em substituição a ela** | **Bug real**: o JSX é `{rows.length === 0 ? <EmptyState message="Nenhuma obrigação" /> : null}` seguido, incondicionalmente, por `<OperationalTable>...<tbody>{rows.map(...)}</tbody></OperationalTable>` — quando `rows.length === 0`, o usuário vê a frase "Nenhuma obrigação" **e, logo abaixo, uma tabela com cabeçalho e nenhuma linha** (`PayablesListPage`/`InvoicesListPage.tsx:154-182`, função `PayablesListPage`). Em todas as outras 8 listagens do app, o padrão é sempre "OU empty state OU tabela", nunca os dois juntos — este é o único ponto onde a tela mostra as duas coisas ao mesmo tempo, parecendo um erro de renderização |
| ApQueuePage | `EmptyState` + `orientation` ("Limpe os filtros ou aguarde novas emissões.") | Boa, mutuamente exclusiva com a tabela |
| PaymentsListPage | `EmptyState` + `orientation` | Boa |
| ShipmentsListPage | `EmptyState` + `orientation` | Boa |
| CustomsListPage | `EmptyState` com `title` **+** `message` **+** `action` (botão "Novo processo") | **Melhor caso do app** — é a única listagem cujo empty state inclui um botão de ação direta embutido no próprio componente, não só texto |
| MovementsPage | `EmptyState` com `title` + `message` | Boa |
| OrderCockpitPage (sub-tabelas: faturas, obrigações, pagamentos, candidatos) | **Não usa `EmptyState`** — texto solto `<p className="muted">Nenhuma fatura</p>` etc. | Inconsistente com o padrão da própria página (usa `EmptyState`/`ErrorState`/`LoadingState` para o carregamento geral, mas cai para `<p>` cru nas 4 sub-listas internas) |
| CustomsDetailPage (faturas, embarques, alocações vinculadas) | `<p className="muted">Nenhuma fatura vinculada.</p>` — sem `EmptyState` | Mesmo padrão "mais pobre" do restante do módulo de Aduana |
| 4 painéis de Aduana (Doganale/Numerário/Nationalization/Receipt) | **Usam `EmptyState` com `title`+`message`** (ex.: "Sem liberações" / "Crie uma liberação após submeter o processo.") | Nuance importante: os 4 painéis de Aduana são, neste ponto específico, **mais cuidadosos que a própria `CustomsDetailPage`** que os contém — a página-mãe usa texto cru para suas próprias listas, mas os painéis-filhos usam o componente correto |
| ShipmentDetailPage (itens, volumes, referências) | `EmptyState` message-only em todos os 3 casos | Boa, consistente |
| SkuPositionPage (buckets) | `EmptyState` com `title` ("Sem saldo") | Boa |

**Conclusão 7.1**: o componente `EmptyState` é usado na maioria dos casos, mas 3 pontos (`OrderCockpitPage` sub-tabelas, `CustomsDetailPage` suas próprias listas) caem para texto solto sem o componente — e um ponto (`PayablesListPage`) tem um bug real de renderização dupla (mensagem + tabela vazia simultâneas).

## 7.2 Loading de tabela/página

Já detalhado com precisão em `PRE_PREENCHIMENTO_EDICAO.md` (seção B), resumo aqui:

- **Nenhuma tela do app usa skeleton loading.** Nenhuma usa spinner/ícone giratório. 100% dos estados de carregamento são o componente `LoadingState`, que é uma linha de texto (`<p className="muted">Carregando…</p>`).
- **6 das 7 listagens** (`OrdersListPage`, `InvoicesListPage`, `PaymentsListPage`, `ShipmentsListPage`, `CustomsListPage`, `MovementsPage`) zeram seus dados (`setRows(null)`/`setRows(undefined)`) antes de cada busca — inclusive ao trocar um filtro — e o `return` condicional de loading está **acima** do cabeçalho/filtros no JSX, então a tela inteira (título, KPIs, filtros) some e reaparece do zero a cada troca de filtro. Não é só na carga inicial — é a cada refinamento de busca.
- **1 exceção real: `ApQueuePage`.** Não zera `data` antes de recarregar, só alterna uma flag `loading`. Resultado: ao trocar de filtro, a tabela **antiga** continua visível, sem nenhuma alteração visual (sem opacidade reduzida, sem overlay), enquanto o texto "Carregando contas a pagar…" aparece acima dela. Não é "tabela desaparece e reaparece" nem "opacidade reduzida" — é uma terceira variante não prevista nas opções do roteiro original: **texto de carregamento simultâneo a uma tabela desatualizada e com aparência normal**, o que pode levar o usuário a interagir com uma linha que já não corresponde ao filtro atual.
- Em nenhum caso os campos de filtro ficam `disabled` durante a busca — em todas as telas, inclusive `ApQueuePage`, dá para clicar em outro filtro chip enquanto a busca anterior ainda está em voo (não há debounce nem bloqueio, o que pode empilhar requisições concorrentes — ver risco de corrida documentado em `PRE_PREENCHIMENTO_EDICAO.md`, seção A).

## 7.3 Validação de formulário

- **Quando dispara**: majoritariamente **no submit** (clique no botão de ação), não em `onBlur` nem em `onChange`. Exemplos: `OrderCreatePage.addLine()` só valida `qty <= 0` e SKU inexistente quando o usuário clica "Adicionar linha"; `saveDraft()` só valida `code` vazio e "nenhum item" ao clicar em "Salvar rascunho"/"Salvar e confirmar"; `OrderDetailPage.onCancel()` só valida o motivo de cancelamento (obrigatório se `CONFIRMED`, máx. 64 caracteres) ao clicar em "Cancelar". Não há nenhum exemplo de validação em `onBlur` de um campo individual mostrando erro *enquanto* o usuário ainda está no formulário, exceto o caso nativo do atributo HTML `required` em alguns `<input>` (que dispara o balão nativo do navegador ao tentar submeter um `<form>` de verdade — só se aplica aos poucos formulários que usam `<form onSubmit>` de fato, como `PaymentCreatePage`; a maioria das telas usa `<Button onClick={...}>` fora de um `<form>`, então nem o `required` nativo do navegador atua).
- **Onde aparece o erro**: sempre no mesmo padrão — um `Notice tone="danger"` (ou o componente `ErrorState`/`error` genérico) **no topo da seção relevante da página**, nunca abaixo do campo específico que falhou, e nunca como toast/notificação flutuante (não existe nenhum componente de toast no projeto). Exemplo real de mensagem: `"SKU não encontrado — crie o produto abaixo ou escolha um existente"` (`OrderCreatePage.tsx:98`) e `"Motivo do cancelamento: máximo 64 caracteres"` (`OrderDetailPage.tsx:121`).
- **Campo com erro**: quando o componente `TextInput`/`SelectField`/`MoneyInput` recebe a prop `invalid`, a borda muda para `var(--color-danger-fg)` via classe `.ds-input--invalid` (`index.css:725-727`) e `aria-invalid` é setado. **Na prática, porém, a prop `invalid` quase não é usada nas telas revisadas** — a grande maioria dos erros de validação (SKU não encontrado, motivo obrigatório, quantidade inválida) é comunicada **só pelo `Notice` de erro no topo da seção**, sem marcar visualmente qual input específico está errado. Não há ícone de erro dentro do campo em nenhum caso observado.
- **Resumo**: validação client-side existe, mas é escassa (a maior parte da validação de negócio acontece no servidor e retorna como erro de API — ver 7.4), dispara só no submit, e quando dispara não aponta visualmente para o campo específico — só para uma mensagem de texto genérica no topo da seção.

## 7.4 Erro de API no submit

- **Padrão universal em todas as ~20 telas de escrita**: `try { await apiCall(); } catch (e) { setError(e instanceof Error ? e.message : "Erro"); } finally { setBusy(false); }`. O erro é sempre capturado e mostrado **inline**, dentro da própria página, via `Notice tone="danger"` (ou `error error-state` no caso do componente `ErrorState`) — **nunca como toast**. Não existe nenhum componente de notificação flutuante/toast em todo o projeto (confirmado — não há `Toast`, `Snackbar`, ou `sonner`/`react-hot-toast` no `package.json` nem em `ui/`).
- **O que acontece com os dados já digitados quando a API retorna erro**: são **preservados** — em nenhum dos fluxos revisados o formulário é limpo após uma falha de submit. Isso é um ponto positivo consistente do app: o usuário pode corrigir e reenviar sem redigitar tudo.
- **Tratamento especial de conflito de versão (HTTP 409 — optimistic concurrency)**: presente em `OrderDetailPage` (confirmar/cancelar), `InvoiceDetailPage` (salvar itens/condições), `PaymentDetailPage` (alocar), `ShipmentDetailPage` (11 ações via `handle409`) e `CustomsDetailPage`/4 painéis (via `conflictMessage()`). Em todos os casos, a mensagem de erro é razoavelmente informativa (ex.: `"Conflito de versão — estado recarregado. Revise e tente de novo (rascunhos locais preservados quando aplicável)."`), mas como documentado em `PRE_PREENCHIMENTO_EDICAO.md`, o "recarregamento" desses fluxos **sobrescreve incondicionalmente outros campos do formulário que não têm relação com o conflito** — ou seja, o tratamento de erro em si é bom (mensagem clara, não perde o que causou o conflito), mas o efeito colateral do recarregamento pode apagar edições não relacionadas em outros campos da mesma tela.
- **Erros de permissão (403)**: tratados de forma diferente conforme o módulo — `SkuPositionPage`/`MovementsPage`/`CustomsListPage`/`CustomsDetailPage` detectam especificamente `status === 403` e mostram uma mensagem amigável ("Sem permissão para estoque.", "Sem permissão para processos aduaneiros."); as demais telas não distinguem 403 de qualquer outro erro — mostram a mensagem crua vinda da API (`e.message`), que pode ser um texto técnico do backend em vez de uma frase pensada para o usuário final.
- **Erro de rede (sem resposta do servidor)**: só é tratado explicitamente em um lugar — `LoginPage.onSubmit()`, que detecta `err instanceof TypeError` e mostra "Falha de rede. Verifique a conexão e tente novamente." (`LoginPage.tsx:51-52`). Em nenhuma outra tela do app existe esse tratamento específico — um erro de rede em qualquer outra ação de escrita cai no `catch` genérico e mostra `e.message`, que para um `TypeError: Failed to fetch` nativo do browser é uma mensagem técnica em inglês, não uma frase compreensível para o usuário final.
